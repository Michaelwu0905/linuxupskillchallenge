## 简介

你可能一直是以普通用户身份登录服务器的，但你大概已经知道 [root 才是 Linux 系统上的超级用户](https://www.ssh.com/academy/pam/root-user-account#what-is-a-root-user?)。这个管理账号，也就是“超级用户”账号，权力无限——命令里打错一个字就可能让服务器瘫痪。作为系统管理员，你通常是在既重要又远程的系统上工作，所以避免这类错误是*一个非常好的主意*。

在久远的年代，系统管理员在生产系统上直接以 `root` 登录，但现在通行的最佳实践是不鼓励甚至禁止直接用 `root` 登录，而是授予指定的可信用户通过 `sudo` 命令运行仅限 root 的命令的权限。

## 本地更改 vs 全局更改

**全局**：任何用户都可以使用的程序/环境，在整个系统中使用。全局更改会影响所有用户。

**本地**或**按用户**：某个特定用户运行的程序/环境，其他用户不可用。本地更改只影响一个用户。

## 你是谁，你能做什么？

Linux 系统中有 3 类用户：

* `root`——强大的超级用户，可以在系统的任何层级执行任何命令。他们既可以做所有全局更改，也可以为任何用户做本地更改。
* `sudoers`——被允许使用 `sudo` 的普通用户，也就是说，他们可以在系统的一个或多个层级执行命令，可以做部分或全部全局更改。通常至少会有一个与 root 拥有相同权力的 sudoer，但其他 sudoer 拥有的特权数量可能各不相同。
* `普通用户`——可以使用系统但只能做本地更改的用户，也就是只能处理自己的文件/目录和环境变量。

我们会在[第 13 天](13.md)和[第 14 天](14.md)更详细地介绍用户及其权限。

## 停止使用 root

如果你用[某个大型 VPS 服务商](00-VPS-big.md)创建了虚拟机，`root` 通常已经被“禁用”，而你的默认用户（ubuntu、azureuser 等）已经拥有 `sudo` 权限。

不过，如果你真的、*真的*想用 `root`，在 [AWS](https://tecadmin.net/how-to-enable-ssh-as-root-on-aws-ubuntu-instance/)、[Azure](https://stackoverflow.com/questions/24313562/root-login-ubuntu-vm-on-azure) 和 [GCP](https://cloud.google.com/compute/docs/connect/root-ssh) 上都有办法做到。**但请自担风险！**

不过，如果你是在[本地](00-Local-Server.md)或使用[其他 VPS 服务商](00-VPS-small.md)创建的虚拟机，那么你很有可能随手就能用到 `root` 用户。

停止使用 root。如果你遵循了那些指南，你应该已经创建了一个普通用户并把它加进了 sudoers 组，像这样：

    adduser snori74
    usermod -a -G sudo snori74

把一个普通用户加进拥有 `sudo` 特权的组是最简单的做法，因为 `sudo` 组在 Ubuntu 中相当标准。但这也可以通过用 `visudo` 命令修改 `/etc/sudoers` 来实现。

从现在起用这个新用户登录。用 `whoami` 打印你登录时使用的用户名。

## 修改密码

如果你用密码登录（而不是公钥），那么现在是确保它非常强且唯一的好时机——也就是至少 10 个字母数字字符——因为你的服务器完全暴露在会不断尝试入侵的机器人面前。如果你仍在使用 `root`，这一点尤其重要。

用 `passwd` 命令修改你的密码。

做法是：想一个新且安全的密码，然后直接输入 `passwd`，按“Enter”，在提示时输入当前密码，再输入你选的新密码，确认它——然后把它记在某个地方。当然，在生产系统中，公钥和/或双因素认证会更合适。

## 关于“加固”的一点说明

你的服务器之所以安全，是因为它的安全更新是最新的，而且你设置了*长、强、唯一*的密码——或者正在使用公钥。虽然它暴露在全世界面前，并且很可能持续受到攻击，但它应该是完全安全的。

下周我们会看看如何查看这些攻击，但现在只需强调一点：读一读关于 “SSH 加固”的资料是可以的，但像修改默认端口和 `fail2ban` 这类东西，在我们学习的过程中既不必要也没帮助——不用它们你也完全安全。

## SUDO 的力量

* 用下面 “资源” 部分里的链接了解 `sudo` 是如何工作的
* 试试 `cat /etc/shadow`，你能查看这个文件的内容吗？
* 这个文件保存着哈希后的密码。它是入侵者的首要目标——他们想拿到它并用离线密码破解工具找出密码。所以可以安全地假设，系统中的非授权用户不应该能看到它。
* 现在用 `sudo` 试试，也就是 `sudo cat /etc/shadow`
* 测试运行 `reboot` 命令，然后通过 `sudo` 运行（也就是 `sudo reboot`）

重新连接回来之后：

* 用 `uptime` 命令确认你的服务器确实完整重启了
* 用 `last` 命令并按用户名过滤（例如 `snori74`）查看登录历史。如果这是第一次使用非 root 用户，你只会有一条记录（也就是 `last snori74`）。
* 现在和你以 root 身份登录的时间对比一下：`last root`
* 更好的是，用 `sudo lastb` 检查针对 root 的**失败登录尝试**
* 用命令 `sudo -i` 测试完全“变成 root”。如果你有一系列要“以 root 身份”执行的命令，这会很方便。注意你的提示符的变化。
* 输入 `exit` 或 `logout` 回到你自己正常的 “admin” 登录。
* 输入以下命令查看最近几次 `sudo` 的使用：`sudo journalctl -e /usr/bin/sudo`

*通常调用 `sudo` 命令会要求你重新用密码确认身份。不过，这一点可以在 sudoers 配置文件中改掉，从而让它不提示输入密码。我们会在[第 13 天](13.md)更详细地讨论它。*

## 管理任务

我们会详细讲述你能对服务器做的许多事情，下面是一些需要 `sudo` 的简单管理任务示例。

如果你愿意，现在可以给服务器改名。传统做法是编辑 `/etc/hostname` 和 `/etc/hosts` 两个文件然后重启——但更现代、也更被推荐的做法是使用 `hostnamectl` 命令，像这样：

    sudo hostnamectl set-hostname mylittlecloudbox

不需要重启，但如果你想在提示符里看到新名字，只需用 `bash` 打开一个新会话（或者登出再登录，效果相同）。

对于云服务器，你可能会发现重启后主机名会变回去。要防止这种情况，编辑 `/etc/cloud/cloud.cfg`，把 "preserve_hostname" 那一行改成：

    preserve_hostname: true

你也可以考虑修改服务器使用的时区。默认很可能是 UTC（也就是 GMT）——对于一个遍布全球的服务器集群来说这相当合适。你也可以把它设成服务器所在的时区，或者你和你总部所在的时区。对公司来说这不是能轻率做出的决定，但现在你可以随意修改！

先检查当前设置：

    timedatectl

然后获取可用时区列表：

    timedatectl list-timezones

最后选一个，像这样：

    sudo timedatectl set-timezone Asia/Shanghai

确认：

    timedatectl

这样做的主要实际影响是：（1）计划任务的时间，（2）`/var/log` 下日志文件的时间戳。如果你做了改动，记录的日期和时间自然会出现一个“跳跃”。

## 权力越大，责任越大

作为 Linux 系统管理员，你可能在客户或定制系统上工作，对它们你几乎没有控制权，而其中很多默认会以 `root` 身份做一切事情。你需要能够在这样的系统上安全工作——此时你唯一的保护就是在按下 `Enter` 之前再检查一遍。

另一方面，对于任何你有完全控制权的系统，推荐为你自己（以及任何共同管理员）设置一个有权运行 `sudo` 的“普通”账号。虽然这在 Ubuntu 上是标配，但在 Debian、CentOS 和 RHEL 等其他流行的服务器发行版上也很容易配置。

即便如此，在做全局更改之前采取必要的预防措施也很重要，以免不小心把自己锁在外面或引发其他问题。使用测试环境、检查语法错误和拼写错误、盯紧日志文件等做法，最终会成为你的第二天性。

### “sudo -i” 和 “sudo -s” 有什么区别？

`sudo -i` 和 `sudo -s` 都是允许用户在基于 Unix 的系统上获得 root 权限的命令。不过它们的工作方式有一些差异。

* `sudo -i` 是 “sudo interactive” 的意思，它会为 root 用户启动一个新的登录 shell。这意味着它为 root 用户创建一个新环境，包含 root 用户的主目录和 shell 配置文件。这与直接以 root 用户身份登录类似，从这个 shell 中执行的任何命令都会拥有 root 用户的权限。
* `sudo -s` 是 “sudo shell” 的意思，它会为 root 用户启动一个新 shell，但不会创建新的登录 shell。这意味着它不会改变当前用户的环境或 shell 配置文件。从这个 shell 中执行的任何命令都会拥有 root 用户的权限，但环境仍然是当前用户的环境。

总结一下，`sudo -i` 更强大，会创建一个拥有 root 用户完整环境的新 shell；而 `sudo -s` 没那么强大，只是启动一个拥有 root 用户权限、但环境与当前用户相同的新 shell。
